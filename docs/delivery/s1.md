## S1.1 signing groundwork — what was built

| Area | Implementation | Requirement |
|---|---|---|
| Signing intent | `/auth/reauth?purpose=SIGN` must name `recordType`, `recordId`, `recordVersion` (400 otherwise). The `SigningIntent` travels with the pending re-authentication into the evidence; `SignatureService` refuses another record or version with `409 ARQ-ESG-004`. Stored on the signature (`signing_intent_id`) and in the REAUTH_SUCCESS / SIGN audit events. ADR 0019 §4 (amended) | URS-ESG-002, ESG-003 |
| Sessions as JSON | `SessionJson` + `springSessionConversionService`: `<class>\n<JSON>`, allow-listed classes only (Spring Security context, OAuth2 authorization request, saved request, our re-auth records, Instant, Duration, Boolean, String); `ArrheniqUser` Jackson mixin. V13 clears the old Java-serialized sessions. ADR 0018 (follow-up resolved) | URS-SEC-005 (ASVS V5.5) |
| Configurable approval | `kernel.esign.ApprovalLevel/ApprovalPolicy/ApprovalService`: tenant setting `approval.<kind>` (site overrides tenant), NONE / SINGLE / DOUBLE; DOUBLE = REVIEWED then APPROVED by a different person (`403 ARQ-SOD-002`); reject supersedes a partial approval. Products use it; specifications and protocols will. ADR 0019 §6 | URS-MD-004, ESG-001 |
| Frontend | Approve sends the record and version to `/auth/reauth`; product page shows "1 of 2 approvals", the next meaning (Reviewed/Approved) and blocks a second signature by the same person; clear message on `ARQ-ESG-004` | |

## S1.3 specifications — what was built

Schema from V4 (`specification`, `spec_version`, `spec_test`); no migration.

| Area | Implementation | Requirement |
|---|---|---|
| Model | A specification (number, title, product) has versions; each version lists tests from the library with product-specific limits: two-sided, one-sided (NLT / NMT), report-only, or a text limit; optional alert limits inside the limits; unit, decimals, replicates and name default to the library test | URS-MD-003 |
| Versions | Only a DRAFT is edited (the whole ordered test list is saved at once; tests left out are logically removed). An EFFECTIVE version never changes: a change is a new version, copied from the effective one, approved again. One open version (DRAFT or IN_REVIEW) at a time (`409 ARQ-MD-020`). Approval makes a version EFFECTIVE today and the previous one SUPERSEDED; existing results keep the version they were tested against. Discard a draft with a reason (discarding v1 discards the specification); retire an effective version with a reason | URS-MD-004 |
| Approval | Same flow as products (S1.1): e-signature bound to the version and its content (test list and limits hashed, hash stored on the version), signing intent, NONE / SINGLE / DOUBLE from `approval.specification`, segregation of duties (author/submitter can't sign) | URS-ESG-001..003 |
| Audit | Every change of a limit is one field in the audit trail, e.g. `test.IMP-B.upperLimit 0.5 → 0.3`; workflow steps SUBMIT, SIGN, APPROVE, SUPERSEDE, REJECT, RETIRE, LOGICAL_DELETE | URS-AUD-001/002 |
| Site scope | Through the product: read `masterdata.view`, edit `spec.manage`, approve `spec.approve`, each at the product's site; other sites see 404 | URS-IAM-005 |
| Retired library tests | Can't be added to a new specification; stay in new versions of specifications that already had them | URS-MD-001 |
| Screens | **Specifications** list (effective version, version in progress); create dialog; detail page with version history, test editor (add from library, limits and alerts inline, reorder, remove), changes against the previous version highlighted, submit / approve / reject / retire / discard, signatures. Product page lists its specifications | |

Tests: `SpecRulesTest` (limit rules, defaults, error positions, retired carry-over), `SpecificationIT` (draft →
review → effective → new version → superseded; one-sided and text limits; audit of a single changed limit; no edits
in review or after approval; one open version; empty draft can't be submitted; SoD; site scope; discard),
`limits.test.ts` (criterion text, version comparison).

Not in S1.3: future effective dates (a version becomes effective on approval), the change-impact preview (S1.4).

## S1.5 protocols — what was built

- **V14** adds the storage condition, change summary and approval date to a protocol version, allows one approved
  version per protocol, and makes time points, tests and grid cells unique among live rows only, so a draft can be
  saved again and again while the replaced rows stay for the audit trail.
- **Protocol builder** (`ProtocolService`, `ProtocolRules`): start from an ICH template (time points, condition,
  study type) and/or a specification version of the same product (its tests, each at every time point). Time
  points are kept in chronological order (days, weeks, months), duplicates such as 3 and 3.0 months are refused,
  each test must run at one time point at least, and a retired library test may only stay in a protocol that
  already had it. Units planned per time point plus a reserve give the planned inventory. The plan warns about
  time points with tests but no units, and time points where nothing runs.
- **Lifecycle**: draft → in review → approved, then superseded by the next approved version or retired; one open
  version at a time; reject, retire and discard need a reason; approval is an e-signature bound to the version
  (setting `approval.protocol`: none, single or double), author and submitter can't approve. The audit trail
  records per-cell changes (`tp.3M.unitsPlanned`, `grid.ASSAY`).
- **Screens**: Protocols list with “New protocol” (product, template, specification), the protocol page with
  versions, the editable test × time-point matrix (click a column header to toggle a whole time point), units
  per time point, totals and warnings, workflow buttons and signatures; a Protocols card on the product page.
- **Tests**: `ProtocolRulesTest` (sorting and grid remapping, error positions, retired tests, warnings),
  `ProtocolIT` (template + specification start, repeated saves, audit keys, approve, new version supersedes,
  validation, empty submit, other-product specification, SoD, site scope), `plan.test.ts`.

Not in S1.5: pulling units or creating studies from a protocol (S2), bracketing/matrixing designs.
