## S2.1 pull-date engine — what was built

- **Engine** (`scheduling.PullDateCalculator`, algorithm `schedule.pull-dates@1.0.0`, ADR 0011): pure and
  deterministic. Calendar date = on-stability date + months (clamped to the month end), weeks or days; then the
  site rules: a site holiday follows `scheduling.holiday_rule`, a Saturday or Sunday its own rule; moving goes
  to the nearest working day (Mon–Fri, not a holiday), so a moved date is never a weekend or holiday. Invalid
  input fails loudly.
- **Settings** (`scheduling.SchedulingSettings`): tenant settings `scheduling.saturday_rule` / `sunday_rule` /
  `holiday_rule` (already provisioned: LEAVE / MOVE_BEFORE / MOVE_AFTER, the eSTAR defaults), overridable per
  site, and the site's `holiday_calendar`. A missing or unknown value is an error, not a default.
- **eSTAR parity:** `EstarPullDates` ports eSTAR's calculation line by line (test code only). `EstarParityTest`
  compares about 800,000 cases (every day of 2020–2030 × typical time points × all nine weekend-rule
  combinations): identical except the two documented corrections in [s2-pull-dates.md](s2-pull-dates.md).
- **Reference cases:** `scheduling/pull-date-reference.csv`, 39 hand-checked cases (month ends, leap years,
  weeks, days, every weekend rule, holidays), each with eSTAR's result where eSTAR has one.
- **Protocol time points are whole numbers now** (`ProtocolRules`): pull dates are calendar arithmetic in whole
  months, weeks or days; 1.5 months has no defined date.
- **Preview:** `GET /api/v1/protocol-versions/{id}/pull-dates?onStabilityDate=…` and a “Pull dates” card on the
  protocol page: pick an on-stability date, see each time point's pull date with its weekday and why it moved.
  Nothing is stored; S2.2 stores schedules.
- **Tests:** `PullDateCalculatorTest`, `EstarParityTest`, `ProtocolRulesTest` (whole numbers), `ProtocolIT`
  (preview with a site holiday and a site-level Saturday rule, site scope, bad dates), `pullDates.test.ts`.

Not in S2.1: a screen to maintain site holiday calendars and scheduling settings (they're in the database and
used by the engine; the admin screen comes with S2.3); pull windows (S2.3).
