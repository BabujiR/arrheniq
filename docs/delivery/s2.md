## S2.1 pull-date engine — what was built

- **Engine** (`scheduling.PullDateCalculator`, algorithm `schedule.pull-dates@1.0.0`, ADR 0011): pure and
  deterministic. Calendar date = on-stability date + months (clamped to the month end), weeks or days; then the
  site rules: a site holiday follows `scheduling.holiday_rule`, a Saturday or Sunday its own rule; moving goes
  to the nearest working day (Mon–Fri, not a holiday), so a moved date is never a weekend or holiday. Invalid
  input fails loudly.
- **Settings** (`scheduling.SchedulingSettings`): tenant settings `scheduling.saturday_rule` / `sunday_rule` /
  `holiday_rule` (already provisioned: LEAVE / MOVE_BEFORE / MOVE_AFTER, the eSTAR defaults), overridable per
  site, and the site's `holiday_calendar`. A missing or unknown value is an error, not a default.
- **eSTAR parity:** `EstarPullDates` ports eSTAR's calculation line by line (test code only). `EstarParityTest`
  compares about 800,000 cases (every day of 2020–2030 × typical time points × all nine weekend-rule
  combinations): identical except the two documented corrections in [s2-pull-dates.md](s2-pull-dates.md).
- **Reference cases:** `scheduling/pull-date-reference.csv`, 39 hand-checked cases (month ends, leap years,
  weeks, days, every weekend rule, holidays), each with eSTAR's result where eSTAR has one.
- **Protocol time points are whole numbers now** (`ProtocolRules`): pull dates are calendar arithmetic in whole
  months, weeks or days; 1.5 months has no defined date.
- **Preview:** `GET /api/v1/protocol-versions/{id}/pull-dates?onStabilityDate=…` and a “Pull dates” card on the
  protocol page: pick an on-stability date, see each time point's pull date with its weekday and why it moved.
  Nothing is stored; S2.2 stores schedules.
- **Tests:** `PullDateCalculatorTest`, `EstarParityTest`, `ProtocolRulesTest` (whole numbers), `ProtocolIT`
  (preview with a site holiday and a site-level Saturday rule, site scope, bad dates), `pullDates.test.ts`.

Not in S2.1: a screen to maintain site holiday calendars and scheduling settings (they're in the database and
used by the engine; the admin screen comes with S2.3); pull windows (S2.3).

## S2.2 study login — what was built

- **Study login** (`study.StudyService`, new module `study`): a lot of an **approved** product, the **effective**
  specification version, and one or more conditions, each an **approved** protocol version of the product with
  the chamber it's stored in (list STORAGE_LOCATION, site-specific). One login creates a study group and one
  DRAFT study per condition (one study per condition per login); units for testing and reserve come from the
  protocol. Required: lot number, on-stability date, reason (STUDY_REASON), study length (STUDY_LENGTH); optional:
  manufacture and expiry dates, your own reference, notes.
- **Study IDs** (`StudyCodes`, URS-STU-002): from `study.code_pattern` (default `YYnnnn` → 260001), year from the
  site's calendar, a counter per tenant and year in `app.tenant_sequence` (row-locked upsert, so parallel logins
  never collide); an ID already taken (e.g. migrated) is skipped; a discarded study's ID is not reused.
- **Workflow:** draft (editable: lot, dates, reason, length, location, reference, notes) → submit → approve by
  e-signature (`approval.study`, default SINGLE; NONE approves on submit) or reject with a reason; discard a draft
  with a reason. The specification and protocol versions must still be in force at submit and approval. Author,
  last editor and submitter can't approve.
- **Schedule generated on approval, in the same transaction** (`scheduling.ScheduleGenerator`, listening to
  `StudyApproved`): one time point per protocol time point with calendar date, pull date, the rule that moved it,
  pull window (± `scheduling.pull_window_days`) and planned units; the algorithm version is stored on the study;
  one audit event lists every pull date. **V15** adds a deferred constraint trigger: an approved study without
  time points can't be committed (URS-STU-005 “DB constraint + test”).
- **Back-entry is refused for now:** if any pull date after the initial one is already in the past at approval,
  the approval fails with `BACK_ENTRY` (and nothing is signed); back-entry with attestation is S2.4.
- **Also:** `GET /api/v1/studies/{id}/schedule`; protocol and specification summaries carry the id of the
  approved/effective version; local demo data adds three stability chambers at NJ (also to existing databases).
- **Screens:** Studies list (status filter, next pull), “Log in study” form, study page (details, other conditions
  of the same lot, planned pull dates for a draft, the stored schedule once approved, signatures, history), a
  Studies card on the product page, studies in the home-page work lists, “Studies” in the menu.
- **Tests:** `StudyIT` (two conditions → two studies with consecutive IDs; approval generates 8 time points and an
  audit event; manager can't approve; SoD; site scope; back-entry refused and rolled back with the signature;
  database refuses an approved study without schedule; 20 parallel logins get unique IDs), `StudyCodesTest`.

Not in S2.2: changing pull dates, windows status (due/overdue), the pull calendar (S2.3/S2.6); termination,
copy and back-entry (S2.4).
